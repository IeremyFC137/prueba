Fundamentos de REST:
- Resources: todo es considerado un recurso, cada recurso se va a identificar con una URL (entidades concretas o colecciones de entidades)

- Interfaz Uniforme: interfaz entre cliente servidor tiene que ser consistente y uniforme para todas las interacciones.
- Separación de conceptos: los componentes de cliente y servidor están separados, ambos evolucionan de forma separada.

✔ Modularidad y reutilización → Separa la lógica común del código principal de la aplicación.
✔ Soporte para síncrono y asíncrono → Algunos middlewares pueden ejecutarse en paralelo para optimizar el rendimiento.

El servidor de desarrollo de Django (runserver) no es eficiente

No maneja múltiples conexiones concurrentes de manera eficiente.
No está optimizado para la seguridad ni la gestión de procesos.
No tiene funciones avanzadas como balanceo de carga o manejo de tráfico estático.

Django necesita un WSGI (Web Server Gateway Interface) o un ASGI (Asynchronous Server Gateway Interface) para manejar múltiples solicitudes simultáneamente.

Django no maneja: ✅ Balanceo de carga (distribuir tráfico entre múltiples servidores).
✅ Caché de contenido estático (CSS, imágenes, JavaScript).
✅ Optimización de rendimiento y seguridad a nivel de red.

Por eso, Nginx o Apache se usan como servidores web frontales que reciben todas las solicitudes y las reparten eficientemente.

Beneficios de usar Nginx con Django
✅ Mejor manejo de concurrencia: Nginx maneja miles de solicitudes simultáneas.

✅ Balanceo de carga: Distribuye tráfico a varios servidores Django/Gunicorn.
✅ Seguridad: Protege Django contra ataques de red, DDOS y permite HTTPS con SSL.

Un servidor de aplicaciones como Gunicorn y un servidor web como Nginx cumplen roles diferentes en el despliegue de una aplicación:

Gunicorn: Ejecuta la lógica de la aplicación, procesando peticiones y conectándose a bases de datos.
Nginx: Se encarga de gestionar tráfico HTTP, servir archivos estáticos y distribuir peticiones a los servidores de aplicaciones.

## **GitHub Actions vs. GitLab CI/CD: ¿Cuál es la diferencia?**

Tanto **GitHub Actions** como **GitLab CI/CD** son herramientas de **automatización y CI/CD (Integración Continua y Entrega/Despliegue Continuo)**, pero hay diferencias clave en su enfoque, funcionalidad y ecosistema.

---

## **📌 ¿Qué es GitHub Actions?**
**GitHub Actions** es una herramienta de automatización integrada en GitHub que permite ejecutar **workflows** en respuesta a eventos como `push`, `pull_request` o `issues`.

🔹 **Características principales**:
- **Integrado en GitHub** → No necesitas configurar un servidor externo.  
- **Basado en YAML** → Se configuran en el directorio `.github/workflows/`.  
- **Eventos automáticos** → Se activan con eventos de GitHub como `push`, `PR`, `tag`, etc.  
- **Marketplace de acciones** → Puedes reutilizar acciones creadas por la comunidad.  
- **Ejecuta en runners de GitHub o auto-hosted** → Usa servidores en la nube de GitHub o en máquinas propias.  
- **Buen soporte para proyectos Open Source** → GitHub ofrece minutos gratuitos para repositorios públicos.  

💡 **Ejemplo de un workflow en GitHub Actions**:
```yaml
name: CI Workflow

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout código
        uses: actions/checkout@v3

      - name: Instalar dependencias
        run: npm install

      - name: Ejecutar pruebas
        run: npm test
```
✅ **Ejecuta el workflow cuando se hace un `push` en la rama `main`**, instalando dependencias y ejecutando pruebas.

---

## **📌 ¿Qué es GitLab CI/CD?**
**GitLab CI/CD** es el sistema de automatización integrado en GitLab que permite definir **pipelines** para compilar, probar y desplegar código.

🔹 **Características principales**:
- **Integrado en GitLab** → Funciona nativamente con GitLab sin necesidad de herramientas externas.  
- **Basado en YAML** → Se configura en `.gitlab-ci.yml`.  
- **Más flexible en runners** → Puedes usar los servidores de GitLab o runners auto-hospedados.  
- **Integración con Kubernetes y Docker** → Ofrece una mejor integración con despliegues en contenedores.  
- **Control total sobre pipelines** → Soporta fases (`stages`) más detalladas en los pipelines.  

💡 **Ejemplo de un pipeline en GitLab CI/CD**:
```yaml
stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - echo "Compilando el proyecto..."
    - npm install

test:
  stage: test
  script:
    - npm test

deploy:
  stage: deploy
  script:
    - echo "Desplegando la aplicación..."
```
✅ **Define un pipeline con las fases `build`, `test` y `deploy`** para ejecutar en GitLab.


## **📌 ¿Cuál es mejor?**
Depende de tu proyecto y necesidades:

✅ **Usa GitHub Actions si...**
- Tu código está en **GitHub** y quieres aprovechar su integración nativa.
- Necesitas **automatizaciones rápidas** sin configurar servidores adicionales.
- Quieres reutilizar **acciones del Marketplace** para evitar escribir código repetitivo.

✅ **Usa GitLab CI/CD si...**
- Tu código está en **GitLab** o necesitas más control sobre los pipelines.
- Necesitas una **mejor integración con Docker, Kubernetes o runners auto-hospedados**.
- Requieres **pipelines más detallados** y avanzados en el proceso de CI/CD.

---

## **📌 Conclusión**
Ambas herramientas son **potentes soluciones de CI/CD**, pero **GitHub Actions** es mejor si trabajas en **GitHub** y buscas simplicidad, mientras que **GitLab CI/CD** es más **robusto y flexible** para proyectos más complejos o que requieren **integración con Kubernetes**.

🔹 **¿Cuál elegir?** → Si usas GitHub, **GitHub Actions** es una opción natural. Si estás en GitLab o necesitas un CI/CD más avanzado, **GitLab CI/CD** es una mejor elección. 🚀

DevSecOps Stages: Secret Management
- Hardcoding secrests in deployed code is a bad idea
- Keeping secrets in code base is also proven to be dangerous
- Process of saving secrets in a secure storage service and accessing those whenever needed, is secrets management

The secrets doesn't have to be managed from the code, they have to be managed by some other way. Secret Storage Services, they stores our secrets and our code can refer to this storage.

Hashicorp Vault
- open-source system to securely storing/accessing secrets
- also supports encryption as a service

But why Vault?
- Moving secrets to one place (Vault)
- Encrypted
 . At rest
 . In transit
- Access Control is provided
- Audit trail

Efimeral Secrets: temporary secrets, issued with a expiry timeline

But how Vault helps in application compromise

- Temporary credentials to apps
 . changes after some interval
- Different tokens for every application/entity/user so easy to know point of compromise
- Also, easy to revoke access selectively
- Bad encryption prevented using Encryption as a service
